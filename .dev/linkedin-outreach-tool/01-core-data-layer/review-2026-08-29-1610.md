# Review — 2026-08-29 16:10 — SP1 (01-core-data-layer)
Diff: main...feat/build-linkedin-outreach-tool   Personas: Bug Hunter, Security, Architect

## Verdict: BLOCK

Two Bug Hunter findings contradict an explicit, load-bearing PRD guarantee ("corrupt week
file must throw, never silently substitute — silently substituting would let a subsequent
write permanently destroy recoverable data"). Both are silent-incorrect-output failure
modes reachable by any caller passing an untrusted/malformed week key, which SP2's HTTP
layer will do directly from a URL parameter. Fix before SP2 builds on top of this contract.

## Must-fix

- [Bug Hunter] `src/lib/weeks.js:133-145` (`readWeek`) — a syntactically-valid-JSON but
  schema-invalid week file (e.g. `{}`, an array, a bare scalar) is silently accepted and
  returned as if it were a real week object, instead of throwing `WeekError`. Verified:
  writing `{}` to `2026-W35.json` and calling `readWeek('2026-W35', config, dir)` returns
  an object with no `version`/`week`/`start`/`end` fields and throws nothing. This is
  exactly the failure mode PRD §4.6/§9 rules out. Fix: after `JSON.parse` succeeds,
  validate the parsed value actually has the week schema shape (at minimum `version`,
  `week`, `start`, `end`, `counts`, `metrics` present and correctly typed) and throw
  `WeekError` if not. Add a test for a syntactically-valid-but-wrong-shaped file (`{}`,
  `[]`, `"hello"`) alongside the existing unparseable-string test in `weeks.io.test.js`.

- [Bug Hunter] `src/lib/weeks.js:12-18` (`isValidWeekKey`) + `weekKeyToRange` — a week
  number that is out of range *for that specific ISO year* (e.g. week 53 in 2023, a
  52-week year) passes validation and produces a self-contradictory week object (`week:
  "2023-W53"` but `start`/`end` dates that actually belong to `2024-W01`). Verified:
  `isValidWeekKey('2023-W53')` returns `true`; `emptyWeek('2023-W53', config)` returns
  `start: "2024-01-01", end: "2024-01-07"`. Every downstream function (`readWeek`,
  `writeWeek`, `emptyWeek`) gates only on this same insufficient check. Fix: `weekKeyToRange`
  (or `isValidWeekKey` itself) must compute the actual number of ISO weeks in the given
  year and reject a week number that doesn't exist for it. Add a test for a well-formed but
  non-existent key (`2023-W53`, `2025-W53`) alongside the existing real-53-week-year tests.

## Notes (non-blocking)

- [Architect] `src/lib/weeks.apply.test.js` — PRD §7 asks for an input-immutability
  ("structuredClone isolation") assertion on *all* mutation functions; only 4 of 9

  identical pattern so this is low-risk, but it's a real, specific gap against a stated
  "all" requirement — worth closing when convenient, not blocking.
